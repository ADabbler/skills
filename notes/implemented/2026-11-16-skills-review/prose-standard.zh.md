# Prose Standard 中文对照

英文技能主文件及全部参考内容的中文对照。实际使用的技能保持英文。

技能描述：在项目与 API 文档、决策记录、代码和测试注释、提示词、描述文本、诊断信息及 CLI/UI 文案中，编写、审查、恢复、精简或审计技术文字时使用。决定何处需要文档或注释时也适用。在保留事实含义的同时，改善清晰度和完整性。

界面短描述：编写和审查技术文本，使表达清晰、信息完整。

## 技能主文件

英文原文：[SKILL.md](../../../skills/prose-standard/SKILL.md)。

保留读者采取行动或维护系统所需的事实。删除不能增进理解的重复内容和编写过程叙述。

### 范围

根据请求和现有上下文确定读者、目的和文件范围，明确后直接推进。审查任务报告发现；获得编辑授权的任务应用修改。

### 保留必要含义

改写前，识别主体与行为、条件、时间、义务或许可、例外、失败、责任与资源归属，以及后果。保留与读者任务相关的事实。

在使用处写清必要行为和限制。已有的架构、算法、扩展理由或示例解释使用链接，避免重复。链接不能替代调用者在本地需要知道的失败条件。与其分成多个章节重复同一事实，不如使用短段落。

遗漏某项理由会导致误用或错误简化时，应说明这一不容易直接看出的理由。代码和类型已能清楚表达的操作，不必再由注释复述。

### 同时检查覆盖与表达

以目标读者需要理解或完成什么来判断完整性。用户文档应提供必要信息，不要求用户查看源码才能理解。获授权编辑时补齐缺失信息，审查时报告缺口。现有句子准确，不等于内容完整。

| 位置 | 需要检查的信息 |
| --- | --- |
| 项目 README | 目的、面向的用户、可用的起点、必要要求与限制、详细指导链接 |
| 配置参考 | 支持的值、默认值、优先级、变更生效时机、无效设置的后果 |
| 架构与设计说明 | 当前结构、职责、重要交互，以及指导维护的理由、权衡和约束 |
| 公共接口文档 | 不同返回结果、失败条件、副作用，以及相关的资源管理、取消、完成或持久化保证 |
| 任务指南 | 前提、实际操作、可观察的成功结果、常见失败的恢复方式 |
| 内部注释 | 影响安全维护、但代码本身不易看出的不变量、资源管理和执行顺序 |
| 测试注释 | 特殊夹具、间接观察方式或平台适配为何必要 |
| 决策与工作记录 | 当前决定或开放问题、不易直接看出的理由，以及恢复工作或重访决定所需的证据和限制 |
| 诊断信息 | 失败的对象或输入、失败原因或违反的条件，以及有帮助的修正办法 |

事实对读者重要、且本地尚未清楚说明时，才应用这些标准。这是覆盖提示，不是必填章节。详略按任务选择，不用常规背景、穷尽式清单或编造内容填充模板。

### 从读者视角表达

- 遵循针对目标文字明确指定的语言。未指定时，保留已有文字或周围内容的语言。新内容没有这类语言上下文时，遵循项目约定；项目也未约定时，使用交流语言。
- 现状文档说明当前行为。决策和历史记录可以保留有用的背景或备选。提案保留不确定性，事故复盘保留因果顺序，冻结快照遵循其保存规则。
- 原地替换过时描述。
- 优先使用具体的主体和动作。技术术语准确指向实际对象时应保留。
- 围绕读者任务组织：先给依赖步骤所需的上下文，例外紧邻它限定的行为；标题帮助读者找到答案。
- 同一概念保持名称一致，命令、选项和标识符与实现一致。目标读者需要时解释不熟悉的术语。
- 界面文案遵循项目已有风格；没有规定时，英文标签采用句首大写，产品名称和标识符保持原样。
- 直接说明选定行为和相关约束。只有相关理由有助于读者作决定或避免合理可预见的错误时，才提及已放弃的备选方案。
- 纠正任务中不必要的额外添加时，描述预期结果。纠正行为本身不足以成为特性标签、PR 中的卖点、解释性注释或永久规则的依据。
- 限制和排除说明应有事实依据，并帮助读者判断适用性、行为或后果。只为区别无关或已放弃想法的排除说明应删除。

### 核对相关事实

依据实际来源核对命令、默认值、限制和行为。区分源码检查、模拟验证和真实执行。明确不确定的说法，外部调用遵循授权范围。

修改工具会解释执行的文字前，先核对其含义。保留有效的指令，以及 lint 抑制、类型检查例外和覆盖率排除的必要理由。

对于生成的文字，追溯其来源和受影响的输出，再修改源内容并按需重新生成。在实际使用位置检查摘要和复用片段，确保它们保留读者所需的信息，不依赖完整原文。

冻结归档与第三方材料遵循项目规则。产品消息、诊断和模型提示词会影响行为，其修改须处于已授权的行为范围内。

### 按需读取参考

- 判断完整性与简洁性时，参考下文“表达判断示例”。
- 遇到草稿编号、评审叙述、变更故事或依赖会话的引用时，参考下文“会话痕迹与过度删减”。

最后检查含义、引用和适用性。缺陷与未验证的说法应给出具体证据。格式与链接检查只能证明结构，不能证明语义正确。

## 表达判断示例

英文原文：[examples.md](../../../skills/prose-standard/references/examples.md)。

### 保留时序与失败行为

原文：“导出器谨慎地写入临时文件，仅在写入成功后替换目标，并将失败报告给调用者。”

适度精简：“导出器写入临时文件，仅在写入成功后替换目标，并将失败报告给调用者。”

过度删减：“导出器保存文件。”这丢失了中间写入位置、替换条件和失败报告方式。

### 说明配置顺序的后果

如果配置已经列出顺序，再写“先加载策略插件，再加载工具插件”没有增加信息。

有用的说明：“先加载策略插件，再加载工具插件，使工具写入经过权限检查。”

### 保留本地必要行为

不充分：“见取消设计笔记。”

适度：“取消会中止请求并等待工作任务退出。资源管理和竞争处理见设计笔记。”

### 描述有用的限制

有用：“应用在启动时读取配置；配置变更需要重启。”

与用户指导无关：“私有辅助函数以后应该统一名称。”

### 说明采用的设计

分散注意力：“应用在启动时读取配置，不使用已经放弃的文件监听机制。”

有用：“应用在启动时读取配置。”

比较有助于读者理解权衡或避免误用时，说明备选方案。

有用的排除说明：“预览只显示计划变更，不写入文件。”读者会依赖这项保证决定是否执行命令。

### 纠正无用添加，不制造长期要求

任务是添加 CSV 导出。代理额外添加了未被要求的仪表盘，随后在纠正时移除了它。

最终描述：“添加 CSV 导出。”

“添加不带仪表盘的 CSV 导出”，或专门解释为何排除仪表盘的注释，保留的是代理的绕路过程，而非有用的产品信息。长期限制应有独立的需求或证据依据。

### 保留验证范围

只在 Linux 上测试后写“所有平台都可用”，没有依据。

准确表述：“Linux 安装流程已验证；Windows 和 macOS 尚未验证。”

### 理由须有证据

如果代码只能证明超时为 30 秒，就记录这一事实。将“平衡性能与可靠性”归为当时的设计理由，需要证据支持。

## 会话痕迹与过度删减

英文原文：[session-artifacts.md](../../../skills/prose-standard/references/session-artifacts.md)。

没看过原始讨论的读者，能否理解事实、找到引用并核查证据？按含义判断，不按关键词机械删除。

| 可疑文字 | 处理方式 |
| --- | --- |
| “按评审 C2”或“设计讨论第 7 项” | 引用读者能访问、名称明确的记录，或独立陈述必要事实 |
| 在现状说明中写“本 PR 新增……” | 直接说明当前有效机制 |
| “审查者确认这是安全的” | 写出安全成立的条件；没有独有信息时删除 |
| 注释仅复述循环、分支或断言，没有解释价值 | 保留不易看出的约束或验证理由；教程和算法说明中确有教学作用的步骤与推理应保留 |
| “目前大概够用” | 说明已知边界和不确定性 |
| “使用 A，不使用 B”，其中 B 是已放弃且无关的想法 | 说明 A；排除 B 对读者任务有意义时，才保留 B |

应保留：

- 运行时顺序，例如“旧连接排空后，新连接才接受请求”。
- 回归条件，例如“没有去重时，同一任务可能运行两次”。
- 测量来源、版本、规模和条件。
- 与文档目的相关且有效的 issue、标准和历史证据引用。
- 提案中的真实不确定性，以及事故记录中的因果顺序。

覆盖率排除理由若说明某分支依赖当前不可用的平台，可能同时承载可执行指令和维护约束。应依据代码和测试环境核对理由，保留有效指令及其必要解释。理由错误时，根据证据修正排除规则或解释，不能将其当作评审叙述自动删除。

精简前，确认义务仍是义务、提案仍是提案，证据仍保有来源。
